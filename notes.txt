I won't do retrospection, for all previous thoughts, just log them when (if) they are back. The current thing is about open loop clients.

See the atomic broadcast part of BigBFT is borrowed from Narwhal/Bullshark, which deploys open loop clients, so that even if some proposed blocks are not committed eventually. If BigBFT follows the same practice, the latency may constantly increase as the system runs, because more and more transactions are queued between consensus and execution.

Bullshark is pure atomic broadcast work. The protocol ends at the point the block is committed, which is inside the scope of the consensus protocol itself. So, if the consensus cannot catch up to the request rate, the block interval will build up, and nodes can easily decrease (or sustain a stable) workload by discarding transactions before proposing new blocks.

BigBFT is a replication work, the ordered transactions need to be executed, and by all signs the execution will probably not keep up with the ordering. If there is no proper back pressure from execution to consensus, consensus will not slow down according to execution throughput, the latency will keep increase and not stabilize.

There are two approaches. One is to add the back pressure, the other is to switch to close loop clients, which naturally comes with back pressure.

For the first approach, I need the consensus to be aware of the progress of execution. I need to set up signals that "permit to execute more", and consensus decides the timing to propose blocks according to not only how itself is going but also how execution is going. Alternative to signal I can also just implement consensus and execution as one big state machine, so consensus can directly query execution's progress from the shared state, but that is a bad idea obviously.

For the second approach, I need to implement "lossless" replication i.e. all transactions are executed without the need of retrying, so the latency will not be affected by the choice of retry timeout. This means the Bullshark implementation must commit every proposed blocks, without either giving up certify them or garbage collect the pending-delivery blocks (either certified or not). I have currently done this, but the first approach seems to make more sense after I came up with it. So I will need to try it instead.

The problem when combining Narwhal, RocksDB and large number of nodes. RocksDB demands larger blocks, because that produces largely batched multi_get, results in higher (SSD read) concurrency and higher throughput. However, in Narwhal, the blocks come from every node. With more nodes, there must be more blocks. If you force same number of blocks, you must increase block time, results in unaffordable latency. As the throughput bottleneck-ed by the execution (i.e. RocksDB), it must substantially apply back pressure to Narwhal so that the ordering throughput (in the term of transactions/second) is capped at RocksDB's capacity as the number of nodes grows, or the latency will not converge. Bounded transactions/second + increasing blocks/second = smaller block => poorer RocksDB performance. Thus, performance is not scalable.

Now I start to consider sharded blockchain and cross shard transactions, which may inevitably force the whole system to go (back to) close loop. The root problem is that for any participant in a distributed transaction, it cannot locally figure out whether the participated transactions will be even finished (either committed or aborted) or not if the (client) coordinator may abandon the transaction orchestration at any point and the other participants may (or may not) discard the same transaction sent to them.

I don't find a good way to deal with distributed transactions with current style of one-shot, never retry clients. Any potential solution involves some form of "lossless" where either clients or replicas (or both) would "insist" on the initiated transactions. If so, fixed sending rate will probably unfit, and we basically have to go close loop.

On the other hand, going close loop, which requires replicas to commit every proposed blocks, could be easier than what I previously thought. The key is to shutdown f (faulty) nodes, so only minimum number of the blocks required to progress is proposed. I also need to adjust Bullshark's leader blocks to avoid long period without leader blocks. Other than that, we can only see what's going wrong.

Now we go back to the client scalability. Every message received by the same client lines up, even if they are replies for concurrent requests that are independent to each other. The client-side queuing increases latency, and that increment becomes significant when client needs to process massive number of replies per request (e.g. 67, notice that it is 2f+1 instead of f+1. For the late messages client still needs to recognize them to be late and discard explicitly). For open loop settings this is less a trouble. The new requests depart at fixed rate unconditionally. If client is receiving the amount of replies it is not capable to process, those replies are just queued up (actually on replica side, the back pressure eventually ends in the replica's unbounded sending queues), resulting in constant throughput with even-increasing latency.

However, now we are close loop. The delay of processing replies causes the delay of departing new requests, and finally capped the throughput (while lucky or not the latency will be stable for sure). I even see the throughput changes in second-scale period, whose explanation could be that after committing a batch of requests, the lately-arriving f replies of those requests block clients from committing any later-issued requests. I probably should orchestrate only f+1 replies for each request anyway.

I will need to increase the number of clients per instance. One client worker that controls all of them should be fine and preferred for centralized state management. The replies of different requests will land in different connection stream queues and different client receiving queues and will not impede each other (except for processor time).

Client worker needs to manage state. Currently it is just latency recording, but soon I should implement multi-stage transactions and client worker will need to keep track on their progress as well. By the way, I borrow the name "client worker" from DSLabs where each client worker operates one client. Now the thing is different as discussed, I think I should switch the name to e.g. "workload".

Essentially, there are three components. There are (dumb) clients who work with opaque requests and replies and never interpret them (except check whether the replies match). They perform the "send one receive N" loops and deal with the network. There are workloads who drive the transactions by invoking the clients. They are specific to the transactions, so I will need to implement several workloads for all combinations of YCSB-T/UTXO and sharded/unsharded. Finally, there is a controller that issue transactions to and collect latencies from the workloads. Under the close loop setting, I can simplify by letting the workloads to self-issue, virtually collect latencies with a shared mutable state, and the controller only needs to schedule concurrent workload tasks at the task layer.

Just realize I made a mistake. The only thing that is consistent across the replicas is the block order. I cannot put all the blocks committed at the same time into a fetch batch, because that can result into inconsistent fetch batches on the replicas.

Ok, well, I probably _can_ issue the RocksDB multi_get with keys gathered from multiple blocks, but I will need to split the get results back to block level and push them per block.

Well, I can also just ignore this with current settings. Because of the settings the DAG shape is highly constraint: it's always a fully-connected mesh, with 2f+1 vertices per round. So that for each committed leader block, its causally-dependent subgraph will be consistent on every node. It is impossible to have one node committing a batch of nodes while the other node is not (and only committing the batch as part of the next batch), because if the other node does not commit this batch, the next batch, whose commitment depends on the next block proposed by the other node which depends on the node collecting all blocks of this batch, cannot be committed. This reasoning is very subtle, but I will accept it for now. This work's focus has never been the consensus part.

Now the prefetch. While full replication does not require prefetch, I still need to implement prefetch at execution instead of inside Big storage because prefetch requires execution to explicitly issue ahead fetching, e.g. fetch #2 before post #1, fetch #3 before post #2, etc.

Just realize that it is different between fetching concurrently to executing and concurrent fetches. Currently only one of the execution and storage proceeds at any time. The blocks come in (to execution), execution prepares the fetching key list, then execution pauses and storage starts to work on the keys' values. After storage responds with the values the execution resumes and the storage is idle waiting for the next fetching batch.

By simply (and statically) offset the fetch requests by 1 (or more precisely, -1), as my example above, the execution and storage can already proceed concurrently. Firstly execution works on #1 and storage works on #2 at the same time, then execution works on #2 and storage works on #3 at the same time, etc. The faster of the two will need to wait for the slower one, but the slower one can work for all the time instead of waiting for the faster one as current.

What I have been thinking for a long time is to further parallelize storage (assuming it is the slower one of the two) (hopefully is since parallelize execution would be much more harder) (through parallelize storage is not too easy neither). So that the faster of the two will also be working for all the time. As it turns out, this is not a must for improving performance based on current level.

If execution is dominating the work time, then anything regards to storage will not be significant. On the other hand, if storage is dominating the work time, then concurrently fetching would be necessary because execution takes no time would not be significant if it is already taking minor time.

However, the current status is that when execution takes ~7s in a run storage takes ~12s, so simply overlapping the two may actually yield a big improvement (and consume the majority of optimization space). Seems lucky but I should not feel lucky for getting to know my work instead of not needing to work.

It turns out that 100KB key value pairs was a critical choice for my previous, acceptable performance (~300K/s). With larger values (either because of larger actual values or proofs attached), performance drops a lot. I will need to tweak the skewness to reduce the number of keys to send, so the total amount of data transferred should be the same.

Previously, each key value pair is 100 bytes. Now the key is still 16 bytes, while the value is 1000 bytes. At the same time, there is a Merkle proof which contains log2(100_000) - 1 = 16 SHA256 digests = 512 bytes. In total that is 1528 bytes, >15x than before.

On the other hand, previously every key value pair is transferred from one of the nodes to every node. So the performance will recover if at most 1/15 keys are cache missed and need to be transferred.
